# M2 实施计划：FIFO 调度内核与网站雏形

## 目标

用已验证的 M1 场景数据生成第一份可执行、可复核的 FIFO 基线方案，并让浏览器中的运行态控制台直接展示算法输出，为后续 OR-Tools 优化方案建立稳定对照组。

## 技术方案

### 调度内核

- 按 `release_at`、`task_id` 对任务进行确定性 FIFO 排序，不使用 AI。
- 只选择资源类型匹配、容量足够且状态可用的资源。
- 使用区域移动时间图计算最短移动时间。
- 资源选择按“最早完成时间、资源 ID”确定，保证重复运行结果一致。
- 服务必须在任务截止时间和资源可用时间内完成，否则任务保持未分配并记录原因。

### 独立约束检查

计划生成后重新检查：

1. 任务和资源引用存在；
2. 资源类型及容量匹配；
3. 任务不早于释放时间开始且不晚于截止时间完成；
4. 资源任务和移动区间不重叠；
5. 区域移动时间、服务时长和资源可用窗口一致；
6. 同一任务最多分配一次。

有任一硬约束违规时，计划状态不得标记为可执行。

### 事件后场景

- 延误事件顺延对应航班的登机、出发和未锁定任务截止时间。
- 登机口变更事件更新航班登机口，以及仍指向旧登机口的未锁定任务。
- 原始基线场景保持不变；事件应用生成新版本场景，用于前后对比。

### 网站雏形

- React + TypeScript + Vite。
- Python 脚本导出 `frontend/public/demo-output.json`。
- 首屏为安静、密集的机场运行控制台，不制作营销落地页。
- 第一版实现三种方案切换、指标、事件、未分配任务、任务时间线和资源利用率。

### CP-SAT 优化

- 使用 Google OR-Tools CP-SAT 建模任务选择、资源分配、任务顺序和区域移动时间。
- 目标按“P1 关键任务数—总完成数—优先级得分—等待与移动成本”分层求解。
- 求解结果仍交给独立约束检查器复核，优化器不能自行豁免硬约束。
- OR-Tools 只安装在项目 `.venv`，避免与全局环境的 protobuf 依赖冲突。

## 风险与应对

| 风险 | 应对 |
| --- | --- |
| FIFO 被误认为最终优化算法 | 界面同时展示 FIFO 与 CP-SAT，并分别标注算法名称 |
| 前端指标与后端不一致 | 所有演示数据由 Python 脚本生成，前端不重新计算核心指标 |
| 移动时间图不连通 | 将任务标记为未分配并返回 `no_route`，不使用默认猜测值 |
| 扰动覆盖原始数据 | 事件应用使用深拷贝并递增场景版本 |
| 示例被误认为真实数据 | 强制展示 `synthetic` 分类和虚构 `SIM` 航班编码 |

## 验收标准

- 相同输入重复运行得到字节级稳定的核心计划内容。
- 合法可执行方案硬约束违规数为 0。
- 资源不足、无路线、时间窗冲突均有可测试的未分配原因。
- 事件后计划能体现登机口和任务目的区域变化。
- 网站能在桌面和移动视口显示非空主界面，且核心控件可操作。
