# M3 实施计划：FastAPI 业务闭环与前后端最小联调

## 1. 阶段结论

M3 的目标不是继续扩展调度算法，也不是提前制作完整运行态界面，而是把 M2 已验证的场景模型、FIFO、事件应用、CP-SAT 和约束检查封装为稳定的业务 API，并让现有网站通过 API 获取同一份展示契约。

阶段完成后，应同时具备两条可验证路径：

1. 不依赖前端，使用 FastAPI/OpenAPI 或自动化测试完成“导入场景 → 生成 FIFO → 注入事件 → CP-SAT 重规划 → 比较方案 → 查询审计”的业务闭环。
2. 使用根目录一键启动脚本同时启动后端和前端，网站优先读取 API；后端不可用时回退到已提交的静态演示 JSON，并明确标识当前数据来源。

## 2. 输入、产出与非目标

| 类别 | 内容 |
| --- | --- |
| M3 输入 | M2 的 `Scenario`、`Plan`、FIFO、CP-SAT、`apply_events`、硬约束检查器和 `DemoPayload` 契约 |
| 核心产出 | FastAPI 应用、场景内存仓库、版本化事件应用、计划生成与查询、方案比较、审计记录、统一错误响应 |
| 联调产出 | 前端 API 客户端、静态 JSON 回退、数据源状态、Vite 代理、前后端一键启停 |
| 测试产出 | API 单元/集成测试、完整工作流测试、前端回退测试、启停冒烟测试、原有 19 项回归 |
| 文档产出 | OpenAPI 契约、README 运行说明、M3 review、项目进度记录 |

M3 明确不做：

- 不接入自然语言 AI；AI 事件解析留在 M5。
- 不保存姓名、证件号、联系方式等个人信息。
- 不接入真实机场生产数据或控制系统。
- 不实现登录、角色权限、多人协同和公网生产鉴权。
- 不在本阶段重做整套前端交互；完整运行态操作台属于 M4。
- 不引入 SQLite；第一版使用进程内仓库，重启后恢复只读演示场景。SQLite 在 API 契约稳定后接入。

## 3. 完整业务流程

| 顺序 | 操作 | 系统行为 | 可核验证据 |
| --- | --- | --- | --- |
| 1 | 导入场景 | 严格校验 `Scenario`，保存不可变基线，将场景内事件登记为“待应用” | 返回场景 ID、当前版本、待应用事件 ID |
| 2 | 生成 FIFO | 在指定场景版本上运行 FIFO，执行独立约束复核并保存计划 | 返回 `Plan`，违规数必须为 0 |
| 3 | 注入事件 | 校验 `expected_version`，应用待处理事件或新结构化事件 | 生成新场景版本和审计记录 |
| 4 | 优化重规划 | 在新版本上运行 CP-SAT，再次执行硬约束复核 | 返回新 `Plan`，携带场景版本 |
| 5 | 比较方案 | 比较两个不可变计划的完成率、P1 完成率、等待、利用率和违规 | 返回绝对值及差值，不由前端重新计算 |
| 6 | 查询审计 | 按时间读取导入、事件应用、规划和比较记录 | 能还原本次演示操作顺序 |

## 4. 架构与职责

```text
React 网站
  ├─ /api/v1/demo 优先
  └─ public/demo-output.json 离线回退
             |
FastAPI 路由与统一错误处理
             |
应用服务：场景 / 事件 / 规划 / 比较 / 审计
       |                         |
内存仓库（版本和不可变结果）      M2 调度内核（保持纯函数）
                                 ├─ FIFO
                                 ├─ apply_events
                                 ├─ CP-SAT
                                 └─ validate_plan
```

职责边界：

- 路由层只处理 HTTP、请求模型和状态码，不直接编写调度逻辑。
- 应用服务负责版本检查、业务编排、错误转换和审计。
- 仓库负责保存不可变基线、场景版本、事件状态、计划和审计记录。
- M2 调度函数继续接收/返回 Pydantic 模型，不依赖 FastAPI 或仓库。
- 前端只展示后端返回的指标和差值，不复制调度或统计公式。

## 5. 场景版本与事件语义

这是 M3 最重要的数据一致性规则。

### 5.1 场景聚合状态

每个导入场景在内存中保存：

- `baseline`：不可变的原始场景数据。
- `event_catalog`：导入时已有事件和后续新增的结构化事件。
- `applied_event_ids`：按实际应用顺序保存的事件 ID。
- `current_version`：当前版本号。
- `revisions`：已物化的场景版本快照。

### 5.2 防止重复应用

- 不允许在已经被事件修改过的场景上再次调用“应用全部事件”。
- 每次生成新版本时，都从不可变 `baseline` 出发，只重放 `applied_event_ids` 中的事件。
- 同一事件 ID 对同一场景最多应用一次，重复请求返回 `409 event_already_applied`。
- 一次事件批次只让场景版本增加 1；计划生成和方案比较不改变场景版本。
- 所有写操作携带 `expected_version`。请求版本落后时返回 `409 version_conflict`，且不修改任何状态。

### 5.3 不可变计划

- 计划创建后不修改，始终记录 `scenario_id` 和 `scenario_version`。
- 重规划创建新计划，不覆盖旧计划。
- 只允许比较同一场景下的两个已保存计划；跨场景比较返回业务错误。

## 6. API 契约

统一前缀：`/api/v1`。

### 6.1 端点规划表

| 方法与路径 | 用途 | 主要输入 | 成功响应 |
| --- | --- | --- | --- |
| `GET /api/v1/health` | 存活检查 | 无 | `200`，服务名、版本和状态 |
| `GET /api/v1/demo` | 提供现有网站契约 | 无 | `200 DemoPayload` |
| `POST /api/v1/scenarios` | 导入场景 | 完整 `Scenario` | `201 ScenarioRecord` |
| `GET /api/v1/scenarios` | 场景摘要列表 | `offset`、`limit` | `200 ScenarioListResponse`，包含总数和可规划摘要 |
| `GET /api/v1/scenarios/{scenario_id}` | 查询当前或指定版本 | 可选 `version` | `200 ScenarioRecord` |
| `POST /api/v1/scenarios/{scenario_id}/events/apply` | 应用待处理或新增结构化事件 | `expected_version`、`event_ids`、`events` | `200 ScenarioRecord` |
| `POST /api/v1/scenarios/{scenario_id}/plans` | 生成 FIFO 或 CP-SAT 计划 | 版本、算法、求解上限 | `201 PlanRecord`，包含完整计划与普通语言指引 |
| `GET /api/v1/scenarios/{scenario_id}/plans` | 查询场景计划摘要 | 可选版本/算法筛选 | `200 PlanListResponse` |
| `GET /api/v1/plans/{plan_id}` | 查询完整计划 | 计划 ID | `200 PlanRecord` |
| `POST /api/v1/scenarios/{scenario_id}/comparisons` | 比较两个已保存计划 | 基线和候选计划 ID | `201 PlanComparison` |
| `GET /api/v1/scenarios/{scenario_id}/audit-records` | 查询审计时间线 | 可选 `limit` | `200 AuditRecord[]` |

M3 不提供删除和任意修改接口，避免场景、计划和审计链在契约尚未稳定时出现不可追溯状态。

M3-3 根据“开箱可用、状态可理解”的产品原则细化响应：应用启动时加载内置仿真场景；`ScenarioRecord` 明确所选/当前版本、可用版本、待处理/已应用事件、进程内存储和安全提示；摘要返回任务、资源、区域、事件数量、可规划状态、数据缺口与确定性下一步建议。上述信息均由结构化规则生成，不依赖 AI 文案。

### 6.2 关键请求模型

`ApplyEventsRequest`：

```json
{
  "expected_version": 1,
  "event_ids": ["EVT-DELAY-SIM102"],
  "events": []
}
```

- `event_ids` 用于应用导入场景中已经登记的待处理事件。
- `events` 用于提交新的结构化 `FlightEvent`；M5 的 AI 解析结果最终也进入这里。
- 两者至少有一项非空，且事件 ID 不得重复。

`CreatePlanRequest`：

```json
{
  "expected_version": 2,
  "algorithm": "cp_sat",
  "max_time_seconds": 5.0
}
```

- `algorithm` 只允许 `fifo` 或 `cp_sat`。
- `max_time_seconds` 仅对 CP-SAT 生效，M3 限制在合理范围内，防止误请求长期占用求解线程。

### 6.3 统一错误格式

```json
{
  "error": {
    "code": "version_conflict",
    "message": "场景当前版本为 2，请刷新后重试",
    "details": [],
    "request_id": "REQ-..."
  }
}
```

| HTTP 状态 | 场景 |
| --- | --- |
| `400` | JSON 可解析但业务请求无意义 |
| `404` | 场景、版本或计划不存在 |
| `409` | 场景 ID 重复、版本冲突、事件重复应用 |
| `422` | Pydantic 字段、时间、引用或枚举校验失败 |
| `500` | 未预期服务错误；响应和日志不得泄露本地路径、密钥或个人信息 |

FastAPI 默认验证错误也必须转换为上述统一格式。内部日志保留 `request_id`，公开响应使用安全摘要。

## 7. 新增模型

| 模型 | 关键字段 | 作用 |
| --- | --- | --- |
| `ScenarioRecord` | 当前场景、当前版本、待应用/已应用事件 ID | 场景查询主响应 |
| `ScenarioSummary` | ID、名称、版本、数据分类、任务/资源数量 | 列表轻量响应 |
| `ApplyEventsRequest` | `expected_version`、事件 ID、新事件 | 结构化事件注入 |
| `CreatePlanRequest` | 版本、算法、求解上限 | 计划生成 |
| `PlanSummary` | ID、版本、算法、状态、核心指标 | 计划列表 |
| `PlanComparison` | 两计划 ID、指标原值、差值、结论标签 | 后端统一计算对比结果 |
| `AuditRecord` | ID、动作、时间、版本前后、相关实体、摘要 | 可复核操作链 |
| `ApiErrorResponse` | code、message、details、request_id | 统一错误契约 |

业务模型继续继承严格 `ModelBase`，禁止未知字段。审计摘要只记录匿名任务/场景/计划 ID，不记录旅客个人信息。

## 9. 前端最小联调方案

1. 新增单一 `loadDemoPayload()`，先请求 `/api/v1/demo`。
2. API 请求失败时读取 `demo-output.json`，并返回 `source: "static_fallback"`。
3. API 成功时返回 `source: "api"`；页面以低干扰状态标签显示“服务数据”或“本地演示数据”，并在侧栏同步说明连接状态。
4. API 与静态文件都失败时才进入现有错误页，重试按钮重新执行完整加载链。
5. 开发环境使用 Vite `/api` 代理，避免开放任意 CORS；部署环境优先使用同源反向代理。
6. M3 不在前端增加场景编辑、事件表单和方案创建面板，这些交互在 M4 使用本阶段 API 实现。

## 10. 一键启停升级

M3-7 已将现有脚本从“单 Vite 进程”升级为“后端 + 前端”服务组：

1. 从 `8000-8020` 选择后端端口，启动 `uvicorn backend.app.main:app`。
2. 等待 `/api/v1/health` 返回 200；失败时停止已创建的后端进程并输出日志。
3. 将后端地址通过 `VITE_API_TARGET` 传给 Vite 代理，再启动前端。
4. 等待前端页面返回 200 后才打开 Edge。
5. `.runtime/server-state.json` 升级为带 `schema_version` 和 `services[]` 的状态，分别记录前后端 PID、进程名、启动时间、端口和日志。
6. 停止脚本逐项校验身份后按“前端 → 后端”顺序停止；任何未知 PID 都不结束。

## 13. 风险与处理

| 风险 | 影响 | 处理方式 |
| --- | --- | --- |
| 事件在当前场景上重复叠加 | 延误和截止时间被多次顺延 | 不可变基线 + 已应用事件集合 + 从基线重放 |
| 并发请求覆盖新版本 | 用户基于旧状态生成错误计划 | 所有写操作强制 `expected_version`，冲突返回 409 |
| API 与静态 JSON 字段漂移 | 页面运行时崩溃 | 保留单一 `DemoPayload` 契约和兼容测试 |
| CP-SAT 阻塞异步事件循环 | 健康检查和其他请求卡顿 | 使用同步路由/线程池执行 CPU 工作，限制求解时间 |
| 内存仓库被误认为持久化 | 重启后用户以为数据丢失 | 页面与文档明确“临时会话”，M4 再接 SQLite |
| CORS 配置过宽 | 无必要扩大接口访问范围 | 本地 Vite 代理和部署同源，不使用 `*` 作为默认生产配置 |
| 启动一个服务后另一个失败 | 留下孤立进程或无法停止 | 分阶段健康检查，失败即回收已记录进程 |
| 错误响应泄露路径或输入 | 暴露本机环境或敏感信息 | 统一错误处理，公开摘要与内部日志分离 |
