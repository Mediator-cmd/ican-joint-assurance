# M4-6 实时系统总验收审查记录

## 1. 审查结论

M4-6 已完成，M4 实时运行与动态重规划阶段的九项硬性退出条件均有自动化和真实浏览器证据。六条固定扰动可以在 08:00 至 08:52 依次、一次性生效；每条事件均生成唯一候选并在独立硬约束复核后等待人工决定；全部事件处理后，权威时间继续单向推进至 09:30 完成，不循环、不回绕。

验收期间发现并修复了一个真实边界问题：采用第一条事件候选、拒绝第二条事件候选后，第三条事件曾因已开始任务的路线事实不一致而无法产生安全候选。修复后，拒绝候选仍保留旧当前方案，已经开始的执行路线以当前方案为权威，后续未来任务继续基于最新事件场景进入 CP-SAT 和独立硬约束校验。

本单元只收口 M4，不接入 AI、真实机场生产数据、随机或无限事件、多 worker、PostgreSQL，也没有增加前端时钟、业务状态机或规划器。

> 仅供教学仿真与辅助决策使用，不构成真实机场运行、放行、登机、改签或车辆控制指令。

## 2. 自动化总验收

- 新增 `tests/test_m4_acceptance.py`，通过公开 REST API 在隔离 SQLite 和可注入假时钟上连续执行三轮六事件流程：全采用、采用/保留交替、重置后再次全采用。
- 三轮共生成 18 个互不重复的候选；每轮均到达场景 v7 和 09:30 `completed`，六条事件全部 `resolved`，当前方案硬约束违规为 0。
- 验证冻结任务在候选中的完整分配不被改写，至少一项任务和一项资源均经历三个以上运行状态，完成后再次读取时间不回退。
- 审计记录准确包含 18 次 `event_batch_applied`、18 次 `candidate_created`、3 次 `runtime_completed` 和 2 次 `runtime_reset`。
- 错误候选 ID、陈旧 revision 和待确认状态下重复开始均返回 409，失败前后权威快照完全一致，不产生部分写入。
- 两个独立 TestClient 对同一会话读取完全一致；其中一个客户端采用候选后，另一个客户端刷新到同一 revision、状态和当前方案。

## 3. 审查发现与修正

事件 2 会更新场景中的任务路线。用户拒绝事件 2 候选时，当前执行方案按契约保持不变，但事件和航班事实不能回滚。随后部分任务按旧当前方案开始并被冻结；事件 3 到达后，重规划输入中的场景路线已经更新，而冻结分配仍保留旧执行路线，完整计划复核因此报告 `task_route` 违规并安全暂停。

`apply_runtime_event_batch` 现按以下规则处理：

- 任务一旦进入冻结集合，其当前执行方案分配就是已经发生的路线事实。
- 应用下一批事件前，先把冻结任务的场景起点和终点与当前分配对齐，再锁定任务。
- 冻结任务或当前分配缺失时明确失败，不猜测路线。
- 拒绝的候选不会被静默采用；事件和航班事实不回滚；未开始任务仍使用最新场景重新求解。
- 新候选仍必须通过完整独立硬约束校验，违规方案不能进入待确认状态。

新增 `test_reject_then_later_event_still_creates_safe_candidate` 固化“采用一次、拒绝一次、继续到第三事件”的回归路径。修复后第三事件进入 `awaiting_confirmation`、场景 v4，冻结任务路线与当前执行分配一致，候选违规为 0。

## 7. 已知边界与下一入口

- 当前是 6 条固定、有限、一次性的合成事件，不随机生成或循环播放。更大、更多样的场景属于 M6 规模测试，不应在前端制造伪实时变化。
- SQLite、单 Uvicorn worker 和内存 SSE 缓冲满足本地比赛演示；多 worker、消息总线和 PostgreSQL 不在当前范围。
- 当前不接入真实机场生产流、旅客个人信息或任何控制系统。未来真实数据接入必须另做授权、脱敏、契约、审计和安全隔离设计。
- M5 是下一唯一入口，只实现自然语言事件的结构化解析、缺失字段追问、调度目标选择、方案解释和无模型回退。AI 不得直接修改运行状态或生成未经 Pydantic、CP-SAT、独立硬约束校验和人工确认的执行方案。
