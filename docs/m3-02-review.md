# M3-2 审查记录：场景仓库、版本与审计

## 审查范围

- 进程内场景聚合和线程安全边界。
- 不可变基线、版本快照和防御性深拷贝。
- 待应用/已应用事件状态与新结构化事件登记。
- 版本冲突、重复事件和无效修订的原子失败。
- 审计模型、审计顺序和并发提交。

## 功能审查

| 检查项 | 结论 | 证据 |
| --- | --- | --- |
| 基线不可变 | 通过 | 修改输入、创建返回值或修订返回值均不改变仓库快照 |
| 事件目录分离 | 通过 | 导入事件为 pending；版本 1 的 `Scenario.events` 为空 |
| 历史版本 | 通过 | 版本 1 和版本 2 可分别读取，旧版本不被覆盖 |
| 版本冲突 | 通过 | 过期 `expected_version` 不写版本、事件状态或审计 |
| 事件防重复 | 通过 | 同一事件不能重复应用；无效事件序列不产生部分写入 |
| 新事件登记 | 通过 | 新结构化事件、修订版本和审计在一次锁内提交 |
| 审计稳定性 | 通过 | 时区必填，ID 单调，记录保持写入顺序 |
| 并发安全 | 通过 | 两个线程提交同一预期版本时只有一个成功 |
| 全量回归 | 通过 | 10 项新增测试；项目合计 `35 passed` |

## 关键设计结论

1. 仓库保存的 `baseline` 不携带待应用事件；导入数据中的事件进入独立 `event_catalog`。这能防止规划函数意外应用尚未确认的扰动。
2. 仓库不信任调用者持有的 Pydantic 对象，写入和读取均使用深拷贝，避免列表或嵌套实体被外部原地修改。
3. 修订提交先完成全部检查，再一次性替换事件目录、已应用 ID、版本快照和审计记录；任何异常都不会留下半更新状态。
4. 审计是领域记录而非 HTTP 响应外壳，因此使用独立 `audit_models.py`，仓库不依赖 FastAPI。
5. 计划尚未进入仓库，避免 M3-2 越界；不可变计划存储在 M3-4 与规划服务一起实现。

## 剩余边界

- 当前没有场景 HTTP 接口，仓库异常尚未映射成 404/409。
- 当前只有进程内状态，服务重启后不会保留用户导入场景。
- 仓库只验证修订的版本和事件序列；事件造成的具体航班/任务变化由后续应用服务从基线重放并负责。
- 场景分页、摘要响应和历史版本查询参数属于 M3-3。

## 审查结论

未发现阻塞 M3-2 提交的问题。下一执行单元为 M3-3，只在已验证仓库之上增加场景导入、列表和版本查询路由，不在该单元提前实现事件应用或规划端点。
