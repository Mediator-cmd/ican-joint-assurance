# 联保智调项目总计划

## 1. 项目概述

项目名称：联保智调

项目副标题：航班扰动下特殊旅客地面保障资源优化与推演平台

参赛方向：2026 年 iCAN AI 应用创新挑战赛，软件赛道，交通出行方向。

核心定位：面向机场地面保障人员的仿真与辅助决策系统。系统在航班延误、登机口变更、摆渡资源减少等扰动下，对摆渡车、轮椅、服务人员和特殊旅客服务任务进行约束调度，并给出可执行、可解释、可复核的方案。

安全边界：本项目不接管真实机场运行系统，不提供真实放行、登机或旅客改签决策。比赛版本使用匿名化、历史回放或仿真数据，页面和提交材料均标注“教学仿真与辅助决策用途”。

## 2. 项目目标

### 2.1 比赛目标

- 完成可公网访问的软件演示版本。
- 展示自然语言事件输入、资源优化、异常重规划和结果解释的完整闭环。
- 提供应用方案 PDF、5 分钟以内演示视频、源代码和运行说明。
- 用可重复的仿真数据证明系统相较于 FIFO 先到先服务基线的改进效果。

### 2.2 产品目标

系统需要解决四个问题：

1. 发生多航班延误时，保障人员无法快速掌握任务优先级。
2. 摆渡车、轮椅和服务人员数量有限，人工分配容易发生冲突或超配。
3. 特殊旅客和紧急中转旅客需要不同的保障时限。
4. 新事件发生后，原计划需要快速重排，并且要能说明调整原因。

### 2.3 明确不做的内容

- 不做通用旅行规划或聊天问答产品。
- 不接入真实机场生产系统作为比赛前置条件。
- 不保存姓名、证件号、联系方式等旅客个人信息。
- 不追求一次性为整个机场所有旅客求解全局最优方案。
- 不在第一版实现真实车辆控制、自动放行或自动改签。

### 2.4 与通用 AI 和“套壳作品”的区分原则

本项目的核心价值来自可验证的业务闭环，而不是聊天界面或模型文案。即使完全关闭 AI，系统仍必须能够导入结构化场景、校验数据、生成确定性计划、应用事件、比较指标并查询审计记录。

产品与技术实现遵守以下原则：

1. **工作流优先于聊天框**：核心演示从场景和运行状态开始，不以“请输入问题”作为唯一入口。
2. **确定性能力独立存在**：AI 只降低事件录入和结果理解成本，不能替代 Pydantic 校验、CP-SAT、硬约束复核和版本控制。
3. **结果有证据链**：每个方案都能追溯场景版本、事件、算法、约束检查、指标变化和审计记录。
4. **状态可理解且可行动**：页面和 API 不只报告成功或失败，还要说明任务/资源数量、是否可规划、数据缺口和确定性的下一步建议。
5. **开箱即可体验**：本地启动后提供内置仿真场景；最终界面不要求评委先编写 JSON、API 请求或复杂提示词。
6. **实用性用对照证明**：使用同一场景比较 FIFO 与优化方案的任务完成率、P1 完成率、等待时间和资源利用率，不以泛化建议代替量化结果。
7. **不伪装生产能力**：仿真、内存会话和静态回退必须明确标识，不把比赛演示包装成真实机场生产控制系统。

后续验收除“功能是否存在”外，还要检查首次使用是否有示例、常见错误能否直接定位、用户是否知道下一步，以及 AI 不可用时核心闭环是否仍可运行。

## 3. MVP 范围

### 3.1 场景

第一版只实现一个典型场景：多个航班同时发生延误或登机口变更，机场在一个 15—30 分钟滚动窗口内，为特殊旅客和紧急中转旅客分配有限地面保障资源。

### 3.2 必须实现的能力

- 创建或导入一个扰动场景。
- 展示航班、航站楼区域、服务任务和资源状态。
- 以匿名任务 ID 表示旅客服务需求。
- 使用自然语言输入事件，例如“航班 A 延误 35 分钟，航班 B 更换至东区登机口”。
- 将自然语言转换为结构化事件，并由后端校验。
- 使用优化引擎生成资源分配和任务时间表。
- 检查资源容量、任务时间窗、资源不可重叠等硬约束。
- 展示调整前后等待时间、关键任务完成率、资源利用率和未完成任务。
- 注入新事件后进行滚动重规划。
- 生成一段可供人工确认的任务清单和调整原因说明。

### 3.3 可选增强能力

- 机场平面图上的区域和资源位置展示。
- 服务人员交接班摘要。
- 多方案比较，例如“优先保障关键旅客”和“最小化平均等待时间”。
- 历史事件回放。
- 语音输入和多语言界面。

## 4. 技术架构

```text
React/TypeScript 前端
        |
FastAPI 业务 API
        |
场景服务 ---- 事件解析适配器 ---- AI 模型接口
        |
约束校验 ---- 调度优化引擎 ---- 指标与审计服务
        |
SQLite（开发）/ PostgreSQL（部署）
        |
仿真数据 / 历史回放数据 / 未来机场数据适配器
```

### 4.1 技术选型

- 前端：React、TypeScript、Vite。
- 数据请求：TanStack Query 或等价轻量封装。
- 可视化：ECharts；机场区域图第一版使用 SVG 或 GeoJSON，避免依赖真实机场底图。
- 后端：Python、FastAPI、Pydantic。
- 优化：Google OR-Tools CP-SAT 或线性规划模型。
- 数据库：开发阶段 SQLite，部署阶段保留 PostgreSQL 适配能力。
- 测试：pytest、前端单元测试、Playwright 端到端冒烟测试。
- AI：通过可替换的 OpenAI-compatible 接口接入；无模型或接口失败时使用规则解析回退。

### 4.2 AI 与优化引擎的边界

AI 负责：

- 解析事件描述和调度目标。
- 识别缺失字段并向用户追问。
- 把优化结果转换为自然语言解释。
- 生成交接班摘要和事件报告。

优化引擎负责：

- 资源分配。
- 任务开始和结束时间。
- 资源容量与不可重叠约束。
- 任务优先级、截止时间和公平性目标。

AI 不得直接生成未经校验的调度结果。所有调度结果必须经过结构化校验和硬约束检查。

## 5. 数据模型

第一版使用匿名化和仿真数据，核心实体如下：

- `Scenario`：场景、时间窗口、当前运行模式。
- `FlightEvent`：航班、区域、原计划时间、最新延误、登机口变化。
- `ServiceTask`：匿名任务 ID、任务类型、所在区域、截止时间、优先级、预计服务时长。
- `Resource`：资源 ID、资源类型、当前位置、容量、可用时间和状态。
- `Zone`：航站楼区域及区域间移动时间。
- `Plan`：调度方案、生成时间、方案状态和输入版本。
- `PlanMetric`：等待时间、关键任务完成率、资源利用率、未完成任务数等指标。
- `AuditEvent`：用户输入、系统事件、重规划原因和人工确认记录。

### 5.1 初始数据规模

- 小规模：100 个任务、20 个资源、5 个区域。
- 中规模：500 个任务、50 个资源、10 个区域。
- 大规模演示：2000 个聚合任务、200 个资源、20 个区域。

大规模数据用于验证分区和滚动重规划能力，不代表真实机场生产承诺。

## 6. 调度模型

### 6.1 硬约束

- 一个资源在同一时刻只能执行一个任务。
- 资源服务能力不能超过容量。
- 任务只能分配给具备对应能力的资源。
- 任务必须在可服务时间窗内开始。
- 资源移动时间必须计入任务计划。
- 已锁定或已开始的任务不能被无提示地重新分配。
- 计划输出必须通过完整约束检查，否则标记为不可执行。

### 6.2 优化目标

默认目标按以下优先级排序：

1. 最小化关键任务逾期和未完成任务。
2. 最小化特殊旅客等待时间。
3. 减少资源空驶和区域间移动。
4. 提高资源利用率。
5. 控制不同任务群体之间的服务差距。

### 6.3 计算策略

- 先按航站楼区域和时间窗口分解任务。
- 对当前窗口使用 CP-SAT 或线性规划求解。
- 设置求解时间上限。
- 超时后返回当前最优可行解，并使用启发式算法补全未分配任务。
- 用 FIFO 先到先服务方案作为基线进行比较。

## 7. 阶段流程与里程碑

### M0：需求冻结与仓库初始化

时间：2026-07-27 至 2026-07-29

产出：项目 README、目录结构、需求边界、术语表、Git 分支策略、第一版场景说明。

验收：能够用一页文档说明用户、输入、输出、硬约束和安全边界；不再新增无关业务场景。

### M1：数据模型与仿真场景

时间：2026-07-30 至 2026-08-05

产出：Pydantic 数据模型、JSON/CSV 仿真数据、场景导入接口、数据校验器。

验收：能够导入一个包含航班延误、任务和资源的完整场景，并报告非法数据。

### M2：调度优化内核

时间：2026-08-06 至 2026-08-16

产出：FIFO 基线、优化模型、硬约束检查、指标计算、超时回退策略。

验收：在小规模和中规模数据上生成可行方案；任何有效输入不能产生资源重叠或容量超限；输出可解释指标。

### M3：后端业务 API

时间：2026-08-17 至 2026-08-24

产出：场景管理、事件注入、生成方案、重规划、方案比较、审计记录 API。

验收：不依赖前端即可通过 API 完成“导入—规划—注入事件—重规划—比较”的完整流程。

### M4：运行态前端

时间：2026-08-25 至 2026-09-05

详细实施计划：[m4-realtime-operations-plan.md](m4-realtime-operations-plan.md)

产出：后端权威仿真时钟、运行会话、任务/资源状态机、定时事件自动生效、滚动重规划、人工确认、SSE 实时推送、断线轮询回退，以及运行总览、航班与区域视图、资源面板、任务时间线和动态方案对比。

本阶段的“实时”是可复现的仿真实时运行，不冒充真实机场生产数据。静态演示 JSON 只允许作为服务故障时明确标识的离线只读降级。

验收：评委无需查看代码或手动刷新即可看到仿真时间推进、任务与资源状态转换、事件自动生效、候选方案重新计算和人工确认后的后续执行；关键状态变化不依赖控制台日志。没有完成自动状态推进、事件触发滚动重规划和页面实时更新，M4 不得标记完成。

### M5：AI 事件理解与结果解释

时间：2026-09-06 至 2026-09-12

产出：结构化事件解析、字段缺失追问、调度目标选择、方案解释和无模型回退模式。

验收：至少准备 10 条自然语言事件样例；解析结果必须经过 Pydantic 校验；模型失败时核心调度功能仍可运行。

### M6：规模测试与体验收敛

时间：2026-09-13 至 2026-09-20

产出：大规模场景、性能报告、基线对比、回归测试、部署版本。

开发目标：

- 小规模求解时间不超过 2 秒。
- 中规模求解时间不超过 5 秒。
- 大规模聚合场景在 15 秒内返回可行解或明确的回退方案。
- 硬约束违规数为 0。

这些是项目测试目标，不是对真实机场生产系统的性能承诺。

### M7：比赛材料与最终发布

时间：2026-09-21 至 2026-09-30

产出：应用方案 PDF、5 分钟以内演示视频、稳定公网地址、源代码、运行说明、开发日志、原创证明和风险声明。

验收：在干净环境中按运行说明能够启动；演示流程连续成功三次；提交材料中的项目名称、功能和截图一致；不出现未授权的真实机场或旅客数据。

## 8. 测试与评审策略

### 8.1 功能测试

- 正常场景规划。
- 多航班同时延误。
- 登机口变更。
- 资源不足。
- 任务已开始后再注入事件。
- 无可行方案。
- AI 输入字段缺失或表达含糊。

### 8.2 评审项映射

- 创新性：保障资源、特殊旅客和连续扰动的联合优化。
- 技术实现：结构化事件解析、约束优化、滚动重规划和回退策略。
- 实用价值：减少关键任务逾期和人工重排压力。
- 用户体验：运行态看板、时间线和可解释提示。
- 展示效果：同一场景在人工基线和系统方案之间的量化对比。

### 8.3 安全与合规

- 默认使用仿真数据。
- 所有外部密钥只通过环境变量注入，禁止提交到 Git。
- 不把个人信息写入日志、截图或演示视频。
- 页面和 PDF 显示“仿真训练与辅助决策用途”。
- AI 生成的辅助材料按照比赛要求标注 AI 辅助制作。

## 9. Git 与发布流程

仓库采用单仓库结构，初步目录如下：

```text
docs/
  project-plan.md
  scenarios/
frontend/
backend/
data/
tests/
scripts/
README.md
```

分支策略：

- `main`：可演示、可提交版本。
- `develop`：集成分支。
- `feature/<name>`：单项功能开发。

每个里程碑完成后执行：

1. 单元测试和场景回归。
2. 更新 README 或运行说明。
3. 提交一个可定位的 Git commit。
4. 推送到 GitHub 私有仓库。
5. 记录已知问题和下一阶段入口。

## 10. 首个执行单元

项目执行不直接从 AI 接口开始。第一个工作单元固定为：

1. 初始化 Git 仓库和单仓库目录。
2. 创建第一版 README。
3. 定义 `Scenario`、`FlightEvent`、`ServiceTask`、`Resource`、`Zone` 五个数据模型。
4. 编写一个最小 JSON 场景。
5. 用 FIFO 规则输出第一版任务分配结果。
6. 为该流程添加最小自动化测试。

完成这个单元后再进入优化模型。这样可以先证明数据、业务流程和运行环境完整，再逐步增加算法复杂度。
