# M4 实时运行与动态重规划实施计划

## 1. 阶段目标

M4 要把当前“由 API 加载三套既定快照”的演示页升级为可操作、可复现的仿真实时运行系统。用户启动场景后，仿真时间会持续推进，任务、资源、航班和事件状态会随时间改变；扰动到达后，后端会基于当时已执行的工作自动计算候选方案，并让用户明确确认是否采用。

本阶段完成前，网页不能再以切换固定数据作为主要演示方式。静态 `demo-output.json` 只保留为服务不可用时的只读降级展示。

所有页面和运行响应继续固定显示：

> 仅供教学仿真与辅助决策使用，不构成真实机场运行、放行、登机、改签或车辆控制指令。

## 2. 对“实时”的明确解释

比赛版本的“实时”指可复现的仿真实时运行，不代表已接入真实机场生产系统：

1. 后端维护唯一权威仿真时间，浏览器刷新或多个页面同时打开时不会各自推进出不同时间。
2. 用户可开始、暂停、继续、重置，并选择 `1x`、`5x`、`15x` 仿真速度。
3. 任务和资源状态依据已确认方案的时间边界自动变化，不由前端随机生成。
4. 航班延误、登机口变化、资源不可用等事件在其发生时间自动生效。
5. 事件或关键执行边界触发滚动重规划；CP-SAT 不会在每次页面刷新或每秒时钟变化时重复运行。
6. 后端主动推送最新状态；连接中断时前端短轮询恢复，并明确显示连接状态。
7. 新方案必须先成为“待确认方案”，由用户确认后才替换当前执行方案，不能静默改变正在执行的任务。
8. 事件触发重规划时，仿真在事件发生的准确时刻自动暂停；候选方案确认或拒绝后，由用户明确继续运行，避免阅读期间方案因时间推进而过期。

## 3. 当前版本与目标版本的差异

| 能力 | M3-8 当前状态 | M4 目标状态 |
| --- | --- | --- |
| 时间 | 页面展示场景时间，时间不自动推进 | 后端权威时钟持续推进，可暂停、倍速和重置 |
| 数据读取 | 首次加载或手动刷新 `/api/v1/demo` | 运行快照由后端持续推送，REST 负责控制 |
| 方案 | 三套预先组合的方案快照 | 当前执行方案、待确认候选方案和历史方案动态产生 |
| 任务状态 | 根据固定计划展示安排 | 待出发、前往服务点、现场等待、保障中、已完成、待协调自动转换 |
| 资源状态 | 展示静态负载和任务序列 | 空闲、移动、等待、服务中、不可用及下一可用时间实时变化 |
| 扰动 | 只展示既定事件影响 | 事件到时自动生效，场景版本升级并触发重规划 |
| 断线处理 | API 失败后读取静态 JSON | SSE 断线先轮询恢复；静态 JSON 只作为明确标识的离线只读模式 |

## 4. 用户看到的完整运行流程

```text
选择仿真场景
  -> 创建运行会话
  -> 查看初始方案并确认开始
  -> 仿真时钟推进
  -> 任务与资源状态自动变化
  -> 扰动事件到时生效
  -> 仿真在事件时刻自动暂停
  -> 后端冻结已完成和正在执行的工作
  -> 对未开始任务进行滚动重规划
  -> 页面收到候选方案和变化原因
  -> 用户确认采用或继续原方案
  -> 新方案成为当前执行方案
  -> 继续运行直至完成并生成运行记录
```

评委无需编辑 JSON、打开终端或手动刷新页面，即可看到一次完整的动态变化。

## 5. 运行状态模型

### 5.1 仿真会话

每个运行会话至少保存：

- `session_id`：本次运行的唯一标识。
- `scenario_id` 和当前 `scenario_version`。
- `runtime_status`：`ready`、`running`、`paused`、`replanning`、`awaiting_confirmation`、`completed`、`failed`。
- `simulation_time`、时间锚点和 `speed`。
- 当前已确认执行的 `active_plan_id`。
- 待人工确认的 `candidate_plan_id`。
- 已自动生效事件、已完成任务和正在执行任务集合。
- 单调递增的 `revision`，用于前端去重和断线恢复。

服务器使用单调时钟计算经过时间，避免系统时间校准造成仿真时间倒退。暂停时固定当前仿真时间；切换倍速时先重建时间锚点，再继续推进。

### 5.2 任务状态

任务状态由当前仿真时间、已确认方案和实际执行记录确定：

| 状态 | 用户文案 | 判定原则 |
| --- | --- | --- |
| `pending` | 待出发 | 尚未到移动开始时间 |
| `en_route` | 前往服务点 | 已开始移动，尚未到达任务起点 |
| `waiting` | 现场等待 | 已到达，但尚未到服务开始时间 |
| `in_service` | 保障中 | 服务已开始，尚未完成 |
| `completed` | 已完成 | 服务结束时间已到，并写入完成记录 |
| `unassigned` | 待协调 | 当前确认方案未安排该任务 |
| `affected` | 受扰动待确认 | 扰动已影响未来安排，候选方案尚未确认 |

状态边界必须采用统一的左闭右开规则，确保某一时刻不会同时属于两个状态。刷新页面后，同一会话和同一仿真时间必须得到相同结果。

### 5.3 资源状态

| 状态 | 用户文案 | 页面信息 |
| --- | --- | --- |
| `idle` | 空闲待命 | 当前区域、下一项任务和预计出发时间 |
| `moving` | 前往任务点 | 起点、终点、行程进度和预计到达时间 |
| `waiting` | 现场待命 | 所在区域和预计服务开始时间 |
| `serving` | 保障作业中 | 当前任务、预计结束时间和后续任务 |
| `unavailable` | 暂不可用 | 不可用原因和预计恢复时间 |

现有场景只有区域节点和移动时长，因此 M4 首版展示“区域间移动进度”，不伪造车辆的真实经纬度轨迹。

### 5.4 航班与事件状态

- 航班显示计划时间、当前预计时间、登机口和最近变化。
- 事件依次显示“等待发生、已触发、已应用、重规划中、方案待确认、处理完成、处理失败”。
- 同一事件 ID 只能应用一次；刷新、重连和重复消息不得造成延误或位置变化重复累计。
- 每次事件生效均生成新场景版本和审计记录。

## 6. 滚动重规划规则

动态系统的关键不是重新运行一次现有优化器，而是保护已经发生的事实：

1. 已完成任务保持完成，不能被新方案删除或改写。
2. 正在移动或服务中的任务默认锁定；资源占用延续到当前任务完成。
3. 根据当前仿真时间、资源预计结束位置和下一可用时间构造滚动规划输入。
4. 只重新安排未开始和待协调任务，并应用已经发生的航班、登机口和资源事件。
5. 候选方案生成后再次执行独立硬约束校验；违规不为 0 时不得进入待确认状态。
6. 页面比较当前方案与候选方案，明确显示新增安排、时间变化、资源变化、仍待协调任务和指标差异。
7. 用户确认后以原子操作切换 `active_plan_id`；拒绝时保留当前方案，并记录拒绝原因或默认审计摘要。
8. 若 CP-SAT 超时或无可行解，保留当前执行事实，返回确定性回退方案或明确的人工协调清单。

事件触发重规划期间，运行状态依次进入 `replanning` 和 `awaiting_confirmation`，仿真时间保持冻结。用户采用或拒绝候选方案后，会话回到 `paused`，由用户点击继续；系统不自动越过人工确认点。

重规划触发条件限定为：事件生效、资源状态发生外部变化、当前方案失效或用户明确点击重新计算。普通时钟 tick 和纯展示筛选不得启动优化器。

## 7. 后端接口与推送契约

M4-0 已冻结的完整字段、状态转换、错误码和消息语义见 [m4-runtime-contract.md](m4-runtime-contract.md)。后续实现必须先更新该契约和测试，不能直接在路由或前端另起一套状态。

### 7.1 REST 控制接口

计划新增以下接口，最终路径在 M4-0 契约测试中冻结：

| 方法与路径 | 作用 |
| --- | --- |
| `POST /api/v1/runtime-sessions` | 基于场景和已确认初始方案创建会话 |
| `GET /api/v1/runtime-sessions` | 分页列出 SQLite 中的会话，支持刷新和重启后找回 |
| `GET /api/v1/runtime-sessions/{session_id}` | 获取权威运行快照 |
| `POST /api/v1/runtime-sessions/{session_id}/start` | 开始或继续运行 |
| `POST /api/v1/runtime-sessions/{session_id}/pause` | 暂停并冻结当前仿真时间 |
| `POST /api/v1/runtime-sessions/{session_id}/speed` | 切换 `1x/5x/15x` |
| `POST /api/v1/runtime-sessions/{session_id}/reset` | 明确确认后重置到初始状态 |
| `POST /api/v1/runtime-sessions/{session_id}/replan` | 手动请求滚动重规划 |
| `POST /api/v1/runtime-sessions/{session_id}/candidate/accept` | 原子确认采用候选方案 |
| `POST /api/v1/runtime-sessions/{session_id}/candidate/reject` | 拒绝候选方案并保留当前执行方案 |

所有修改接口携带 `expected_revision`，过期请求返回 `409`，防止两个页面同时操作时互相覆盖。

### 7.2 SSE 推送

使用 `GET /api/v1/runtime-sessions/{session_id}/stream` 建立服务器到浏览器的单向事件流。控制命令仍使用 REST，以便测试、审计和错误响应保持清晰。

事件类型至少包括：

- `runtime.snapshot`：完整运行快照或状态修订。
- `runtime.tick`：轻量仿真时钟同步。
- `task.transition`：任务跨越状态边界。
- `event.applied`：扰动已生效并产生新场景版本。
- `replan.started`、`replan.ready`、`replan.failed`。
- `plan.accepted`、`plan.rejected`。
- `runtime.completed`。
- `heartbeat`：保持连接并帮助判断断线。

`revision` 只标识持久业务状态，`runtime.tick` 和 heartbeat 不增加 revision；每条 SSE 消息另有递增 `sequence`，客户端按 `stream_id + sequence` 去重。SSE 断开后由浏览器携带 `Last-Event-ID` 重连；同一流的缓冲仍存在时补发，否则先发送完整 snapshot。连续失败时每 2 秒读取一次运行快照，恢复连接后停止轮询。静态 JSON 降级必须显示“离线演示，时间不会推进”，不能显示成实时在线。

## 8. 前端交互与可理解性

M4 在现有五个切换页基础上增加统一运行控制条，不恢复长页面滚动：

- 仿真时间、运行/暂停按钮、倍速分段控制、连接状态和场景版本始终可见。
- 总览页显示“现在发生什么、系统正在做什么、需要用户决定什么”。
- 任务页按实时状态分组，并突出下一项即将开始的任务。
- 事件页以时间流展示事件从等待到处理完成的全过程。
- 资源页显示区域间移动进度、当前作业和下一可用时间。
- 方案页显示当前执行方案与待确认候选方案，提供明确的采用和保留按钮。
- 状态变化使用克制的高亮和过渡动画，不能依赖动画才能理解，也不能因文字或徽标变化引发布局跳动。

页面不要求用户理解 SSE、CP-SAT、版本号等实现细节；专业信息放在可展开的依据区，但当前状态、风险和下一步操作必须直接可读。

## 9. 持久化与恢复

M4 接入 SQLite 保存场景版本、计划、运行会话控制状态、关键状态边界、事件处理和人工确认审计；时钟 tick 不逐秒写数据库。

- 正常重启后可恢复到最近一次关键边界，默认以暂停状态等待用户继续。
- SSE 连接、后台任务和浏览器本地状态属于临时运行资源，不写入数据库。
- 单机演示只运行一个后端 worker；多 worker 和 PostgreSQL 适配属于部署扩展，不在比赛 MVP 中虚假承诺。

## 11. 测试矩阵

### 11.1 后端确定性测试

- 使用可注入假时钟验证开始、暂停、继续、倍速切换和重置。
- 覆盖任务与资源每一个边界前、边界时刻和边界后一秒。
- 覆盖两个事件同一分钟发生、事件重复、事件顺序和版本冲突。
- 验证已完成及正在执行任务在重规划中保持锁定。
- 验证候选方案未确认前不改变当前执行计划。
- 验证无可行解、求解超时和服务重启后的安全恢复。

### 11.2 推送与前端测试

- SSE 正常推送、主动断线、自动重连、重复修订和轮询回退。
- 两个浏览器页面同时打开时，时间和状态一致。
- 运行中切换五页、筛选任务或查看详情不会停止时钟或触发重规划。
- 静态降级明确显示离线只读，不能操作运行控制。
- 1440×900 和 390×844 下运行控制条、状态文字、候选方案操作无重叠或裁切。

### 11.3 动态演示验收场景

1. 从 08:00 创建会话并以 `15x` 启动。
2. 页面时间持续推进，任务和资源先后进入移动、等待与服务状态。
3. 08:00、08:04、08:16、08:28、08:40、08:52 六条固定扰动依次自动生效，每条只应用一次。
4. 每条事件均进入重规划并产生唯一候选；候选通过独立硬约束复核后冻结等待人工决定。
5. 用户查看事件事实、完整任务书和真实差异后确认采用；无须调整时也必须明确显示复核结论，不虚构计划变化。
6. 已完成和正在执行的工作不回退，全部事件处理后时间继续单向推进至 09:30 完成。
7. 运行记录可复核六个场景版本、候选、方案和人工确认顺序，完成后不得回到起点。

## 12. M4 硬性退出条件

以下条件全部满足后，M4 才能标记完成：

- [x] 仿真时间可开始、暂停、继续、倍速和重置，且由后端权威维护。
- [x] 至少一条任务和一项资源能在页面上自动经历多个真实状态转换。
- [x] 至少一个定时扰动无需手动刷新即可自动生效。
- [x] 扰动触发滚动重规划，并冻结已完成和正在执行的工作。
