# M4-2 确定性运行状态投影审查记录

## 1. 审查结论

M4-2 已完成。运行会话快照中的任务、资源、航班和事件不再是空数组，而是由会话持久化输入和后端权威仿真时间确定性生成。同一投影依据、同一状态和同一仿真时刻得到完全一致的结果；普通查询不增加 revision，不写控制审计。

## 2. 已实现范围

### 2.1 持久化投影依据

- 每个新会话在 SQLite 保存创建时选择的不可变场景版本、当前确认方案、完整事件目录和已经应用事件的准确 `version_after` 证据。
- `runtime_sessions.projection_source_json` 可空，数据库打开时自动兼容没有该列的 M4-1 旧库。
- 旧会话仍能从 M3 仓储找到场景和方案时，使用专用写入补齐投影依据，不增加业务 revision，也不写控制审计。
- 旧会话无法恢复原方案时继续返回 M4-1 空投影，不使用当前方案或静态演示数据拼装虚假状态。

### 2.2 确定性状态投影

- `ready` 会话只展示已安排关系，不提前把窗口起点任务显示为已开始。
- 开始后，任务按完成、服务、等待、移动、待出发的优先级使用左闭右开边界；未安排任务保持 `unassigned`。
- 资源按不可用、移动、等待、服务、空闲投影，只使用区域节点和百分比进度；零分钟重新定位没有虚假的移动区间。
- 航班在登机开始和预计离港边界切换状态；未应用事件不能提前改写登机口或预计时间。
- 未应用事件在发生时刻进入 `triggered`；已包含在场景版本中的事件为 `resolved` 并携带准确场景版本证据。
- `clock.next_boundary_at` 从任务、资源、航班、未应用事件和场景终点中选择下一个有效边界。

### 2.3 查询与恢复语义

- 运行中快照继续使用 M4-1 单调时钟，不逐秒写 SQLite。
- 纯投影查询不改变持久化仿真时间、revision 或审计数量。
- 投影依据随会话写入 SQLite，因此重启后的新进程不需要重新拥有 M3 方案对象即可恢复完整快照。

## 3. 审查发现与修正

1. 首次专项测试命中了全局 Anaconda，缺少 OR-Tools；确认项目隔离环境为 `.venv` 后改用仓库规定解释器。全局环境未安装或修改依赖。
2. Windows 沙箱拒绝 pytest 临时目录 ACL 访问；在用户明确许可后使用仓库内 `--basetemp` 并在沙箱外运行，测试正常通过。
3. 旧会话不能通过普通控制更新补写投影源，否则会产生虚假 revision 和审计；仓库增加了只允许相同内容重复写入的 `attach_projection_source()`。
4. `ready` 若直接按窗口起点投影，会让用户尚未点击开始就看到服务进行中；现用独立语义保持任务待出发、资源空闲、事件待发生，开始后立即进入准确边界状态。

审查后没有遗留的高、中、低优先级代码问题。

## 5. 已知边界

- M4-2 的 `triggered` 只表示事件发生时刻已到，不应用事件、不升级场景版本、不暂停时钟，也不运行 CP-SAT。
- 当前任务完成状态仍是根据确认方案和仿真时间派生的投影，独立的执行事实持久化与滚动规划输入属于 M4-3。
- M3 场景与计划仓储仍在进程内；M4-2 只保证已创建运行会话所需的投影依据能跨重启恢复。
- 前端仍显示 M3 三套静态快照；SSE、轮询恢复和五页实时交互分别属于 M4-4、M4-5。
- 位置只有区域和进度，不代表真实车辆经纬度或机场生产轨迹。
