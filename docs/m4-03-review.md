## 2. 已实现范围

### 2.1 事件边界与持久化事实

- 运行查询和控制先物化最早可达事件边界，不会因墙钟跨度跨过事件时刻。
- 同一时刻的未应用事件按 `event_id` 稳定排序，只生成一个场景版本和一次自动重规划。
- SQLite 中的运行聚合同时保存初始场景/方案、当前事件场景、当前确认方案、候选方案、冻结任务和事件决定证据。
- 当前 active plan 可以早于事件后的当前场景版本；候选存在时必须严格匹配当前场景版本。
- reset 只从持久化初始事实恢复，不从 M3 当前仓储或静态演示数据重新拼装。

### 2.2 滚动规划与人工确认

- 已完成、移动中、现场等待和保障中的 assignment 逐字段冻结。
- 每项资源从最后一个冻结 assignment 推导下一起点和可用时刻，只优化未冻结任务。
- 冻结 assignment 与未来安排合并后，服务边界再次调用 `validate_plan()`；硬约束不为零的结果按可恢复求解失败处理。
- 手动重规划只允许从 `paused` 发起；每次候选 ID 包含本次 replan revision，同一场景版本可安全重复计算。
- 采用和拒绝同时检查 expected revision 与 candidate plan ID，冲突不产生部分写入。

### 2.3 失败与重启恢复

- 优化器无解、超时或候选硬约束失败时，保留当前方案并回到 `paused`，事件记录显示 `replan_failed`。
- 事件与当前运行事实矛盾或候选状态结构不一致时，会话进入不可恢复 `failed` 并冻结时间。
- SQLite 写入失败不能承诺再写入 `failed`；实际保护是事务回滚、拒绝部分写入并向 API 返回 `runtime_persistence_error`。
- `awaiting_confirmation` 重启后保留候选与投影；中断于 `replanning` 的会话重启后转为 `paused`，允许人工复核后重新计算。

## 3. 审查发现与修正

1. M4-2 要求当前场景与 active plan 同版本，不适用于“事件已发生、候选尚未采用或已被拒绝”的合法状态。运行聚合改为只禁止 active plan 新于场景，并继续要求候选严格同版本。
2. 事件直接修改场景任务路线会覆盖已经发生的 assignment 事实。事件应用现先根据边界投影冻结任务，并让快照优先显示 active assignment 的原路线。
3. 只依赖优化器返回的 `violations` 不能形成独立安全边界。服务层会对合并后的完整方案重新执行 `validate_plan()`，测试也注入了隐藏违规候选验证拒绝行为。
4. 原计划把“持久化失败”和“一致性失败”都描述为进入 `failed`，但数据库不可写时无法安全保存该状态。计划和审查已校正为：一致性失败进入 `failed`；持久化失败回滚并返回错误。
5. 首轮回归后补充了手动重规划遭遇隐藏硬约束违规的测试，因此最终组合基线从 `50 passed` 更新为 `51 passed`，全量基线从 `117 passed` 更新并复验为 `118 passed`。

## 5. 已知边界

- 当前候选需要通过 REST 主动查询，尚无 SSE 推送、消息缓冲、`Last-Event-ID` 重连或轮询回退。
- 前端仍显示 M3 三套静态快照，尚未创建运行会话、控制时钟或展示候选差异；这些属于 M4-4 和 M4-5。
- M3 场景与通用方案仓储仍在进程内；M4-3 只保证已创建运行会话所需的完整事实能从 SQLite 恢复。
- 运行投影只使用区域节点和时间进度，不代表真实车辆坐标、机场生产轨迹或控制指令。
- 当前求解仍是比赛演示规模的确定性单线程 CP-SAT；大规模容量和长时间稳定性将在 M4-6 单独验收。
